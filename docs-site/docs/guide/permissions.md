# 工具授权

普通工具默认自动放行，CHROOT 的普通来源仍按策略绑定，无需到设置页逐来源授权。**Root、Shizuku 和本地 CHROOT 中，能确认宿主系统文件操作只读时默认 `ALLOW`；修改宿主，或未知脚本、动态路径等无法确认是否只读时，先请求审批。** 可选仅本次或本聊天会话同工具、同来源及身份的全部后续宿主修改与不确定操作。项目／全局明确禁止规则、真实系统权限和 Root 总开关仍然有效。

默认允许描述的是权限裁决，不是执行可用性保证。当前工作流仍先捕获所选工作区；若选中的CHROOT尚未创建、状态异常或来源失效，也可能在宿主Root／Shizuku命令进入管理器之前停止。权限按宿主通道核验，不代表会跳过工作区来源检查。

这是**有限静态识别的审批策略，不是运行时拦截或安全隔离**。无法确认是否修改宿主时先审批，实际只读的脚本也可能弹窗；识别器不执行或打开脚本来判定。符号链接、`PATH` 解析和任意程序的实际副作用仍不能保证，不要把提示理解为任意 Root 程序都无法影响手机系统或其他数据。

复杂、高风险、影响共享状态或超出当前任务范围的工作仍需先说明范围并取得相应批准。工具默认允许不等于 AI 可以扩大任务、安装未要求的软件或擅自产生外部费用。

## 计划审批

想先看方案再动手，可以直接告诉 AI：「先只读检查，提交完整计划，等我批准后再改。」复杂、影响面不明或高风险的任务也应先走这一步；已批准且范围未变的方案不必重复提交。

1. **先只读检查**：了解现状、目标、改动范围、风险和验证方式，不先修改文件或执行有副作用的操作。
2. **查看完整计划**：输入区上方出现计划卡，点「查看计划」进入手机／平板适配的审阅面板。
3. **批准执行**：点「批准执行」后，AI 按该方案继续。批准只针对当前计划，没有「始终允许」。
4. **拒绝并结束**：可以先填写拒绝意见，再点「拒绝并结束」。本轮结束、持续目标暂停，不自动重提、消费队列或续调模型；需要修改时再发送新消息。

与计划提交混在同一批的其它工具调用都不会执行，即使它们排在计划之前或只是读取。批准后也不会补跑旧批次，必须重新发起。

每个计划有独立请求，归属发起它的会话；其它会话和子代理不能借用。收起面板不等于批准，停止会清理等待请求。待审批计划仅在本次 App 运行期间保留，重启后不能批准旧卡片。

::: warning 计划与工具策略不同
批准计划不覆盖明确禁止规则，也不代替系统 su／Shizuku 授权、宿主修改／不确定操作审批、插件内容信任或仍适用的 PRoot／SSH 提权审批。宿主会话授权同样不能替代计划审批或扩大任务范围。
:::

## 规则的来源

全局规则来自 App 私有配置目录，本地项目规则来自当前项目的 `.aicode/permissions.json`；SSH 项目规则按既有服务器和项目标识保存在 App 私有目录。选择 CHROOT 不会让规则读取依赖于先创建实例。配置来源失效、解析失败或链接不受支持时，不能把失败当作「没有禁止规则」。

项目或全局 `deny` 可以禁止整个工具或命令段，优先于默认放行和审批。旧配置的 `allow` 项保留供查看／清理，但不改变裁决，也不能免除宿主系统文件审批。规则命中时会返回命中的规则与具体片段，不应改写命令、换工具或修改规则来绕过。

## 宿主系统文件修改与不确定操作审批

识别器检查可解析的直接文件参数、输入／输出重定向，以及内嵌 shell 命令。系统范围包括 Android 系统分区、系统配置／权限数据和内核／设备控制接口，例如 `/system`、`/vendor`、`/product`、`/system_ext`、`/odm`、`/apex`、`/etc`、`/data/system`、`/data/misc`、`/data/adb`、`/metadata`、`/persist`、`/proc`、`/sys`、`/dev`。

- **可确认只读：默认 `ALLOW`**。只因读取宿主系统文件不再逐次询问；仍须满足禁止规则、真实 OS 权限及来源检查。
- **修改宿主：先审批**。包括写入、删除、移动和修改权限／属主等；已有同范围的有效本会话授权时，不重复弹窗。
- **无法确认是否只读：先审批**。未知脚本、任意程序、动态路径或交互输入等无法确认是否修改宿主时属于此类，即使实际只读也可能要求审批，不是“未识别就放行”。
- 仅打印路径字符串不是文件访问；执行 `/system/bin` 中的基础程序也不会仅因可执行文件路径就全部弹窗。正常使用空设备、随机源及本实例私有终端设备不因这些运行设施单独触发审批。
- Root／Shizuku 按宿主命名空间判断。CHROOT guest 自己的 `/etc`、`/usr`、`/var` 写入不等于宿主修改，实际宿主绑定或内核接口按真实来源判断。`apt` 或软件包维护脚本无法确认是否修改宿主时仍可能先询问；首次选择同来源本会话授权可减少后续同工具操作的打断。
- 弹窗显示完整操作和已识别的修改目标或不确定原因，提供**拒绝／仅本次允许／本会话始终允许**。无需先被拒绝再补 `elevate`；该参数不能免除审批策略或越过明确禁止。

::: warning 静态识别不能保证实际副作用
识别器不执行或打开脚本判定，也不是操作系统级文件访问监视器。符号链接及竞态、`PATH` 解析、外部脚本、任意二进制或子进程的实际行为不能保证；未知先审批不代表能捕获全部运行时访问，更不代表安全沙箱。不要运行不可信代码或依赖弹窗保护全部手机数据。
:::

## 高危工具审批与会话授权

宿主修改／不确定操作有两种允许范围：

| 选项 | 范围 |
| --- | --- |
| **仅本次允许（`ONCE`）** | 只批准当前展示的请求，不批准后续命令。 |
| **本会话始终允许（`ALWAYS_SESSION`）** | 本聊天 session、同一 tool、同一 source／identity 的全部后续宿主修改与不确定操作，**包含不同命令和目标，不限当前命令**。不跨工具、来源、身份或父子／其他聊天会话。 |

新的宿主宽范围 grant **仅存内存，进程重启清除**，不从历史或备份恢复。来源、真实通道身份或连接代次、Root 代际、Profile 配置内容或选择、实例改变后需重新审批；不能把旧版 Root／Shizuku 会话记录当作新的宽授权。单次请求或执行许可不得用于变更后的参数和目标；有效宽授权可以覆盖同来源及身份的新命令／目标，但每次仍重新裁决并取得新的内部许可。

每次 Root／Shizuku 执行仍消费一个绑定实际会话、**完整命令**、真实通道身份和当前代际的 one-use 内部 permit，不能换命令、跨会话或重放。它与用户的宽范围 session grant 是两层概念，取得新 permit 不代表必须重新弹窗；宽授权也不是无限 OS Root 权限。

显式 `DENY`、Root 总开关、真实 OS 授权、CHROOT UNKNOWN／清理限制及独立 CREATE／STOP／REMOVE 均不改变；计划、插件信任、插件宿主能力和依赖准备也仍分别决定。行为无法确认只读可以请求审批，但来源、身份或实例／清理状态 UNKNOWN 仍拒绝执行，不能用会话授权解锁。

PRoot／SSH 的显式 `sudo`／`su` 与高危提权仍保留原有行为：可拒绝、仅本次允许，或按**完整精确命令**记住本会话授权，不按前缀、程序名或路径扩大，也不扩展到不同命令和目标。旧 PRoot／SSH grant 不变；子代理及其它会话不继承。

## Root 工具

`Root` 操作**真实宿主 Android**，不是容器 root 或 SSH 的 sudo。设备必须已经取得 root，系统 su 管理器必须允许本 App，并在「设置 → 软件权限」开启默认关闭的 [Root 总开关](/guide/app-permissions#root-总开关)。App 不为设备取得 Root。

- 可确认只读的宿主系统文件操作默认放行；修改宿主或无法确认是否只读时先审批，可仅本次或本聊天会话允许同一 Root 来源及身份的全部后续宿主修改与不确定操作，包含不同命令和目标。
- 每次仍核对完整命令、所属会话、本机身份与代际，再消费仅供本次执行的内部许可；其它命令／会话不能借用。
- 关闭总开关撤销待审批和未使用许可，使相关 session grant 与旧来源绑定失效，并停止本应用管理的 Root 进程。重新开启后只能为新请求签新许可，必要时重新审批，不恢复旧任务或宽授权。
- 停止进程不能撤销已经完成的修改，也不保证终止任意脱离管理的后台进程。
- 总开关、本机授权身份和执行许可不随备份迁移，恢复到其它设备仍须具备真实系统授权。

参数 `command` 为完整命令；`timeout` 以秒计，默认120、上限1800；`elevate` 保留为兼容参数，不再是普通调用或系统文件审批的前提，也不能绕过明确禁止规则和系统授权。

::: warning 输出仍进入 AI 任务
输出有长度上限，不随 SSH 工作区自动归档到远端，但仍会作为工具结果交给你选择的 AI 服务商。处理敏感数据前应确认任务范围，不要把「在手机执行」理解为「输出只留在手机」。
:::

## Shizuku 工具

服务须由你启动并授予本 App 系统权限。ADB shell 和 Root 仍是不同的真实服务身份；默认放行不会把 UID2000 伪造为 UID0，也不保证命令实际可提权。

可确认只读的宿主系统文件操作默认放行；修改宿主或无法确认是否只读时，可仅本次或本聊天会话允许 Shizuku 同一来源及身份的全部后续宿主修改与不确定操作，包含不同命令和目标。服务重启、断连、身份变化和系统撤权使旧内部许可及相关会话授权失效；恢复连接后，新操作按新身份核验并签发许可，不重放旧命令。详见 [Shizuku 工具](/guide/shizuku)。

## 插件操作授权

插件安装／启用的内容信任、插件自身的宿主能力授权和具体通道的默认工具策略是不同层次。本次默认放行不取消插件原生确认、模型／备份／浮层等能力授权，也不让插件借用其它插件的内容信任。

插件可以请求原生审批，但脚本不能替你批准；参数被可写钩子修改后仍须重新判断。插件的 Shizuku 接口仍按插件桥支持范围工作，不因内置工具默认放行而额外获得 Root；桥上仍不允许借 `tools.execute` 调用独立 Root／Shizuku 或计划审批。详见 [插件](./plugins.md)。

## 多会话并行时的授权

每个会话可以独立等待一项审批。弹窗标注发起会话标题，侧边栏等待指示为橙色常亮，处理后显示下一项；不会将一会话的系统文件批准交给另一会话。

计划通知只提示回到 App 审阅，不能在通知上直接批准。停止任务会清理待决请求，拒绝工具审批会结束本轮并取消同批尚未执行调用。

## 页面结构

工具授权页面按「当前项目／全局」列出规则，可折叠、左滑删除，项目规则可以提升为全局。旧 allow 项只供查看与清理，不改变默认策略。

## 高危命令保护

Root／Shizuku／CHROOT 采用上文策略：可确认只读默认放行，宿主修改或无法确认是否只读先审批，可在同工具、同来源及身份下使用有效的本聊天会话宽授权。PRoot／SSH 仍保留灾难性删除和不可静态判断危险命令的旧保护：删除根目录、关键目录或工作区根等操作需按原提权流程处理，不改为宽范围授权。

输出丢弃到 `/dev/null` 本身不要求审批。若命中明确禁止或其它受保护目标，仍分别判断。

## 高危命令提权

PRoot／SSH 的 `Bash`／`terminal` 确需执行被安全检查拦下的操作时，可按原流程携带 `elevate: true` 请求审批或精确匹配会话记录。Root／Shizuku 的 `elevate` 仅保留旧版兼容；本地 CHROOT 也不靠该参数开启普通执行。三通道的宿主修改／不确定操作按上述审批与有效会话授权处理；`elevate` 不能越过显式 `DENY`、总开关或真实系统授权。

## 关于「禁止」规则

一次对话拒绝不产生长期规则。长期规则可手工编辑项目 `<项目根>/.aicode/permissions.json` 或全局 `~/.aicode/permissions.json`，保存后页面自动刷新：

```json
{
  "permissions": {
    "deny": ["Bash(git push)", "terminal(git push)", "Shizuku"]
  }
}
```

不带括号的名称表示禁止整个工具，带括号的命令前缀约束对应工具的可解析执行段，组合命令任一段命中就拒绝。禁止不会被默认放行、旧会话记录或 `elevate` 覆盖。
